# Building Spatz on macOS

These steps build the Spatz toolchain, the Verilator simulator and the
software on macOS, and run programs on the simulated cluster. They were worked
out on macOS 26.6 (Apple Silicon) with Homebrew and Apple clang 17. The
upstream flow targets Linux. On macOS it fails in several places: missing GNU
tools, GCC/Linux-only flags, and a pinned RISC-V GCC that can't be built on
Apple Silicon.

> **Status:** all toolchain pieces except the pinned RISC-V GCC build. The
> simulator `bin/spatz_cluster.vlt` and all software build, and the full
> test suite passes (`ctest`: 164/164, which is 124 riscvTests, 11 snRuntime
> tests and 29 spatzBenchmarks). Every source change in step 7 is
> limited to macOS or behaves the same on Linux, but the changes have only
> been tested on macOS.

## 1. Install the tools

```bash
brew install gnu-sed autoconf automake texinfo coreutils
```

| Package     | Why it is needed |
|-------------|------------------|
| `gnu-sed`   | The toolchain targets run `sed -i 's/.../' file`, which is GNU syntax. BSD `sed` on macOS treats the script as the backup suffix and fails with `invalid command code`. |
| `autoconf`, `automake` | The `verilator` target runs `autoconf` before `./configure`. |
| `texinfo`   | Provides `makeinfo`. Without it, newlib fails with `make[4]: *** [.../libgloss/doc/porting.info] Error 127`. |
| `coreutils` | Provides `nproc`, which `util/Makefrag` calls when verilating. macOS has no `nproc`. |

Put GNU `sed` first on `PATH` whenever you run the toolchain targets, so `sed`
means the GNU version. This avoids patching the Makefile:

```bash
export PATH="$(brew --prefix gnu-sed)/libexec/gnubin:$PATH"
```

## 2. Install the Python dependencies

```bash
pip install -r requirements.txt
```

Without this, the cluster generator (`make generate`, `clustergen.py`) fails
with `ModuleNotFoundError: No module named 'hjson'`. The benchmark data
generators also need `torch`, `numpy` and `scipy` from the same file.

## 3. Install Bender in the expected location

`make all` installs Bender with the upstream init script. If `~/.cargo` exists,
that script installs into `~/.cargo/bin` instead of `install/bender`, and every
later step fails with:

```
bash: .../spatz/install/bender/bender: No such file or directory
```

Fix it with a symlink:

```bash
mkdir -p install/bender
ln -s ~/.cargo/bin/bender install/bender/bender
install/bender/bender --version   # bender 0.32.1
```

## 4. Fetch the hardware dependencies

`make all` never runs `bender checkout`, but the `check-bender` target expects
its result:

```make
ln -s $$(find "$(ROOT_DIR)/.bender/git/checkouts" -type d -name 'spatz_vpu-*') $(ROOT_DIR)/hw/spatz_vpu
```

When `.bender/` doesn't exist, `find` prints nothing, so `ln -s` gets a single
argument and creates a broken `./spatz_vpu` symlink in the repository root.
That's the `?? spatz_vpu` you see in `git status`. The make step then fails
with:

```
find: .../spatz/.bender/git/checkouts: No such file or directory
ln: ./spatz_vpu: File exists
make: *** [check-bender] Error 1
```

Fix:

```bash
rm -f spatz_vpu                  # only the broken root-level link
install/bender/bender checkout   # fetches 18 dependencies, including spatz_vpu
```

After this, `check-bender` creates the correct `hw/spatz_vpu` link.

## 5. Compilers

Leave `CC` and `CXX` unset. `util/Makefrag` sets `CC ?= gcc-11.2.0`, but `?=`
doesn't override Make's built-in defaults (`cc` / `c++`), so all host builds
use Apple clang.

## 6. Build the toolchains

Don't run `make all`: it stops at `tc-riscv-gcc` (see
[RISC-V GCC](#risc-v-gcc-tc-riscv-gcc-does-not-build)). Run the other targets
by name instead:

```bash
export PATH="$(brew --prefix gnu-sed)/libexec/gnubin:$PATH"
export EXTRA_CFLAGS=-Wno-error   # for dtc, see below

make bender
make tc-llvm
make tc-riscv-isa-sim            # apply the Spike patch below first
make verilator
make update_opcodes
```

When everything has built, `install/` contains `bender`, `llvm`,
`riscv-isa-sim` (Spike, `spike-dasm`, `dtc`) and `verilator` (5.034).

### LLVM, newlib and compiler-rt (`tc-llvm`)

This builds clang/lld 22 into `install/llvm`, then newlib and compiler-rt for
both `ilp32d` and `ilp32f` (`install/llvm/ilp32f`). It needs `makeinfo`
(`texinfo`). Without it, pass `MAKEINFO=true` to skip the documentation.

Errors in newlib's `config.log` such as `'ac_nonexistent.h' file not found`
or `unsupported option '-static-libgcc'` are normal autoconf probes, not the
cause of a failure. Look for `***` lines in the `make` output instead.

### Spike (`tc-riscv-isa-sim`)

There are two problems.

**1. `dtc` is built with `-Werror`.** The lexer generated by macOS's old `flex`
then fails:

```
convert-dtsv0-lexer.lex.c:1297:38: error: comparison of integers of different
signs: 'yy_size_t' (aka 'unsigned long') and 'int' [-Werror,-Wsign-compare]
```

The `dtc` Makefile appends `$(EXTRA_CFLAGS)` after `-Werror`, so
`export EXTRA_CFLAGS=-Wno-error` turns the warning back into a warning.

**2. Spike's static libraries contain other static libraries.** The link then
fails:

```
ld: archive member 'libriscv.a' not a mach-o file in 'libspike_main.a'
```

The archive rule in `sw/toolchain/riscv-isa-sim/Makefile.in` passes all
prerequisites, including the dependent `lib*.a` files, to `ar`. GNU `ld`
ignores the nested archives; Apple's `ld` rejects them. Patch the rule to
archive only object files (newer upstream Spike does the same):

```diff
 lib$(1).a : $$($(2)_objs) $$($(2)_c_objs) $$($(2)_lib_libnames)
-	$(AR) rcs $$@ $$^
+	$(AR) rcs $$@ $$(filter %.o,$$^)
```

This patch is in the downloaded clone under `sw/toolchain/` and isn't tracked
by the Spatz repository. Apply it again if you delete and re-download the
clone. `tc-riscv-isa-sim` re-runs `configure` from `Makefile.in` every time,
so you must patch `Makefile.in`, not `build/Makefile`.

### Verilator (`verilator`)

It builds the pinned `v5.034` from `sw/toolchain/verilator` without changes,
once `autoconf` and `automake` are installed.

### RISC-V GCC (`tc-riscv-gcc`): does not build

The pinned `riscv-gnu-toolchain` is GCC **7.1.1** from 2021, and it doesn't
support Apple Silicon as a host. The first failure is in binutils' bundled
zlib, which defines `fdopen` as `NULL` whenever `TARGET_OS_MAC` is set. That
breaks the current macOS SDK's `<stdio.h>`:

```
MacOSX.sdk/usr/include/_stdio.h:322:7: error: expected identifier or '('
zlib/zutil.h:128:33: note: expanded from macro 'fdopen'
```

Patching that would only lead to the next incompatibility, so don't build
GCC. Spatz uses it only for the bootrom, which now falls back to LLVM (step 7).
The software in `sw/` already builds with LLVM.

## 7. Source changes in the Spatz repository

These changes are needed on macOS. Each one is either guarded so it only
applies on macOS, or behaves the same on Linux.

### Bootrom with LLVM: `hw/system/spatz_cluster/Makefile`, `test/bootrom.ld`

The bootrom rule used `$(GCC_INSTALL_DIR)/bin/riscv32-unknown-elf-gcc`,
`-objdump` and `-objcopy`. It now uses them if
`riscv32-unknown-elf-gcc` exists. Otherwise it uses `clang
--target=riscv32-unknown-elf -nostdlib -fuse-ld=lld`, `llvm-objdump` and
`llvm-objcopy` from `install/llvm`.

`test/bootrom.ld` only placed `.text`. GNU `ld` puts the leftover `.rodata`
(which holds `BOOTDATA`) after `.text`, but `lld` puts it first. `BOOTDATA`
then landed at `0x1000`, the boot address where `_start` must be. The
script now lists the data sections inside `.text`, which is harmless for GNU
`ld`:

```diff
-  .text : { *(.text) }
+  .text : { *(.text) *(.text.*) *(.rodata) *(.rodata.*) *(.srodata*) *(.data) *(.sdata*) }
```

The LLVM bootrom has the same layout as the GCC one (`_start` at `0x1000`,
`BOOTDATA` at `0x10e0`). The only difference is one equivalent instruction:
`li`+`slli` instead of `lui`+`addi`, both loading `0x800`.

### C++ standard for `--timing`: `util/Makefrag`

Verilator's `--timing` needs C++ coroutines. The flags were
`-std=c++17 -fcoroutines`, which works only with GCC. With Apple clang/libc++,
`std::coroutine_handle` exists only in C++20, and `verilated_timing.cpp` failed
with `no template named 'coroutine_handle' in namespace 'std'`. On Darwin,
`VLT_CXX_STD` is now `-std=c++20`, used both for `-CFLAGS` and `VLT_CFLAGS`.
On other systems it stays `-std=c++17 -fcoroutines`.

### `uartdpi.c` compiled as C: `hw/system/spatz_cluster/Makefile`

The C file `test/uartdpi/uartdpi.c` was compiled with `$(VLT_CFLAGS)`, which
contains `-std=c++17`. GCC only warns; clang fails with
`invalid argument '-std=c++17' not allowed with 'C'`. The rule now filters out
`-std=c++%` and `-fcoroutines` for this file.

### No `libatomic`: `hw/system/spatz_cluster/Makefile`

The simulator was linked with `-latomic`, which doesn't exist on macOS (the
compiler runtime provides atomics): `ld: library 'atomic' not found`. It's
now added only when not on Darwin.

### Cross-compiling the software: `sw/cmake/toolchain-llvm.cmake`

The toolchain file didn't set a target system, so on a macOS host CMake
assumed a native Darwin build and added `-arch arm64 -isysroot …/MacOSX.sdk`.
The compiler check failed with
`clang: error: unsupported option '-arch' for target 'riscv32-unknown-elf'`.
On an Apple host the file now sets `CMAKE_SYSTEM_NAME Generic` and
`CMAKE_SYSTEM_PROCESSOR riscv32`.

### `dtc` on `PATH` for `fesvr`: `util/Makefrag`

The simulator links against `fesvr`, which is downloaded and configured in
`work-vlt/riscv-isa-sim`. The first `configure` call puts
`install/riscv-isa-sim/bin`, where `dtc` lives, on `PATH`, but the
`$(MAKE) -C …` line that follows did not. With `make sw.vlt -B`, the sub-make
re-runs `configure` and fails with `configure: error: device-tree-compiler not
found`. The `$(MAKE)` line now gets the same `PATH`.

### `mkdir` argument order: `hw/ip/spatz_cc/src/spatz_cc.sv`

The tracer ran `$system("mkdir logs -p")`. GNU `mkdir` accepts options after
operands, but BSD `mkdir` created a directory literally named `-p` in
`hw/system/spatz_cluster`. It's now `mkdir -p logs`.

## 8. Build and run

```bash
cd hw/system/spatz_cluster
make sw.vlt -B                    # simulator + software, as in the README
bin/spatz_cluster.vlt sw/build/spatzBenchmarks/test-spatzBenchmarks-dp-faxpy_M256
```

Expected output:

```
----- (256) axpy -----
The execution took 198 cycles.
The performance is 2585 OP/1000cycle (161%o utilization).
[SUCCESS] Program finished successfully
```

To run every test: `cd sw/build && ctest -j8`. All 164 pass, in about 7 minutes
on an Apple Silicon Mac.

## 9. Waveforms

The testbench can dump the whole cluster while the software holds the
*cluster probe* high. The benchmarks do this around their kernel with
`start_kernel()` / `stop_kernel()` (`sw/spatzBenchmarks/benchmark/benchmark.c`),
so the waveform covers only the kernel, not the boot.

Build the separate tracing simulator once. It uses its own build directory
`work-vlt-fst`, so the normal `bin/spatz_cluster.vlt` stays fast:

```bash
cd hw/system/spatz_cluster
make bin/spatz_cluster_fst.vlt VCD=1
```

Run a benchmark with it. It writes `spatz_cluster.fst` in the current
directory:

```bash
bin/spatz_cluster_fst.vlt sw/build/spatzBenchmarks/test-spatzBenchmarks-dp-faxpy_M256
```

For `dp-faxpy_M256` this takes about 12 s, compared with 1 s without tracing,
and writes about 6 MB. Open the file with GTKWave or Surfer:

```bash
gtkwave spatz_cluster.fst        # or: surfer spatz_cluster.fst
```

If `gtkwave` fails with `Library not loaded: .../libglib-2.0.0.dylib`, the
Homebrew install is stale. Reinstall it (`brew reinstall gtkwave`), or install
Surfer instead (`brew install surfer`).

To dump your own program, write `1` to the `SPATZ_STATUS` register of the
cluster peripheral before the region of interest and `0` after it, as
`start_kernel()` / `stop_kernel()` do. Nothing is dumped if the probe never
goes high.

Changes that make this work:

- **`hw/system/spatz_cluster/Makefile`, `util/Makefrag`:** `VCD=1` adds
  `--trace-fst -DVCD_DUMP -DVCD_DUMP_FILE="spatz_cluster.fst"`, links
  `verilated_fst_c.o` and `-lz`, and switches to `work-vlt-fst` and
  `bin/spatz_cluster_fst.vlt`. `VLT_BUILDDIR` in `util/Makefrag` is now `?=`
  so the Makefile can set it.
- **`hw/system/spatz_cluster/tb/testbench.sv.tpl`:** the dump block called
  `$finish(0)` when the probe dropped. With Verilator this ended the RTL loop
  while the HTIF host side kept waiting for the program's exit code, so the
  simulator hung at 0% CPU. It now only calls `$dumpoff` and lets the program
  finish normally. `testharness.sv` is generated from this template, so run
  `make -B generate` after editing it.
- **`hw/ip/snitch_test/src/verilator_lib.cc`:** the main loop counted time in
  its own `TIME` variable and never passed it to Verilator, so every sample
  was written at t=0 (`%Warning: previous dump at t=0, requesting t=0, dump
  call ignored`). It now calls `Verilated::time(TIME)` before every `eval()`.
  One time unit is half a clock cycle. This also makes `$time` and VPI time
  correct, which Faultergeist needs.

## 10. Notes

- **Regenerating changes tracked files.** `make generate` and `make -B`
  regenerate `src/generated/spatz_cluster_wrapper.sv` and `bootrom.sv`
  from the selected config, by default `cfg/spatz_cluster.default.dram.hjson`.
  They also rebuild `test/bootrom.{elf,dump,bin}`. The committed copies may
  come from a different config (for example DIVSQRT disabled) or from GCC,
  so expect diffs in `git status`.
- **`Warning: Failed to write binary name to logs/.rtlbinary`** appears on the
  first run in a clean directory, because `logs/` is created later by the
  tracer. It's harmless and also happens on Linux.
- **`tc-llvm`** rebuilds LLVM incrementally. It deletes and recreates the
  newlib and compiler-rt build folders, but that is quick.
- **The broken `./spatz_vpu` link** from step 4 gets recreated whenever
  `check-bender` runs without `.bender/` present. Delete it before
  committing.
